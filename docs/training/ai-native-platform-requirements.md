# 综合管理部 AI-Native 平台需求与基建规划

> **版本**: v1.0  
> **基于**: 体系OKR + 各团队AI-Native OKR + RPP/PPT方法论  
> **目标**: 梳理通用平台需求与基建需求，输出可落地执行的里程碑计划  
> **制定日期**: 2026年4月10日

---

## 一、背景与目标

### 1.1 背景

综合管理部作为平台组织，需要为各研发团队（无线、交换机、NMC、IPSIP、会议主机、硬件）提供通用的AI-Native能力赋能。基于：

- **体系OKR**: 研发体系整体AI-Native转型目标
- **各团队OKR**: 6个团队的个性化落地计划
- **RPP方法论**: 优先事项-流程-资源三层诊断
- **PPT方法论**: 人-流程-技术三支柱建设

### 1.2 目标

1. **识别通用需求**: 提炼2+团队共同面临的障碍与需求
2. **规划平台基建**: 明确平台层需要建设的核心能力
3. **制定里程碑**: 输出可执行、可度量的阶段计划
4. **明确依赖关系**: 识别与各团队、基础设施团队的协同点

## 二、需求分析：基于RPP三层诊断

### 2.1 优先事项层（Priorities）- 需求收集与通用性识别

#### 2.1.1 各团队障碍汇总（基于里程碑文档）

| 团队 | 核心障碍 | 具体表现 | 优先级 |
|------|----------|----------|--------|
| **无线** | 无CI/CD基建 | 瀑布模式，缺乏自动化能力 | 高 |
| **无线** | 度量体系缺失 | 无法量化AI-Native效果 | 高 |
| **无线** | 知识库分散 | 管理类需求知识未沉淀 | 中 |
| **交换机** | 技能参差 | 团队AI能力不均衡 | 中 |
| **交换机** | 场景化工具缺失 | 缺乏硬件适配AI工具 | 中 |
| **NMC** | 前后端融合流程 | 需要标准化SPEC流程 | 高 |
| **NMC** | 测试自动化 | 测试左移需要平台支撑 | 高 |
| **IPSIP** | 知识库建设 | 架构知识未系统化 | 中 |
| **IPSIP** | Linter工具 | 架构约束需要工具硬化 | 中 |
| **会议主机** | 度量体系 | 无度量不推进原则 | 高 |
| **会议主机** | 技术债务治理 | 缺乏债务识别工具 | 中 |
| **硬件** | 场景化工具 | 器件/PCB/测试专属工具 | 中 |
| **硬件** | 技能培训 | 硬件工程师AI技能待建设 | 中 |

#### 2.1.2 通用性识别（2+团队共同需求）

**高优先级通用需求（3+团队）**:

| 需求 | 涉及团队 | 通用性 | 平台价值 |
|------|----------|--------|----------|
| **CI/CD平台** | 无线、NMC、会议主机 | ⭐⭐⭐⭐⭐ | 基础设施，全团队依赖 |
| **度量体系** | 无线、会议主机、综合管理部 | ⭐⭐⭐⭐⭐ | 效果量化，决策依据 |
| **知识库平台** | 无线、IPSIP、NMC | ⭐⭐⭐⭐ | 知识沉淀，经验复用 |
| **SPEC流程模板** | 无线、NMC、IPSIP | ⭐⭐⭐⭐ | 标准化流程，降低门槛 |
| **技能培训体系** | 交换机、硬件、无线 | ⭐⭐⭐⭐ | 能力建设，规模化推广 |

**中优先级通用需求（2团队）**:

| 需求 | 涉及团队 | 通用性 | 平台价值 |
|------|----------|--------|----------|
| **测试自动化平台** | NMC、会议主机 | ⭐⭐⭐ | 质量保障，效率提升 |
| **Linter/代码检查** | IPSIP、NMC | ⭐⭐⭐ | 架构约束，质量门禁 |
| **场景化工具库** | 交换机、硬件 | ⭐⭐⭐ | 特定领域效率提升 |

#### 2.1.3 决策过滤器（做什么 vs 不做什么）

**综合管理部平台决策过滤器**:

| 维度 | 做（平台层） | 不做（团队层） |
|------|--------------|----------------|
| **能力类型** | 通用AI能力（Skills/Commands/Hooks/MCPs） | 业务场景定制化开发 |
| **服务对象** | 跨团队通用需求（2+团队共同面临） | 单团队专属需求 |
| **技术范围** | 平台基建、工具链、知识库框架、SDD模板 | 具体业务知识库内容 |
| **流程覆盖** | SDD全流程通用模板（基于集团基线） | 各团队具体流程细节 |
| **基础设施** | CI/CD平台、测试自动化平台、度量平台 | 重复建设各团队独立平台 |

## 三、平台基建需求清单

### 3.1 基础设施层（与基础设施团队共建）

#### 3.1.1 CI/CD平台（高优先级）

**需求描述**: 支持AI-Native研发的持续集成/持续交付平台

**核心功能**:
- AI代码生成流水线
- 自动化测试门禁
- 代码质量检查集成
- 制品版本管理
- 环境一键部署

**涉及团队**: 无线、NMC、会议主机、IPSIP
**共建方式**: 综合管理部提需求，基础设施团队建设
**里程碑**: 
- 4月底: 基础版上线（核心流水线）
- 5月底: 完整版上线（AI-Native特性）

#### 3.1.2 测试自动化平台（高优先级）

**需求描述**: 支持自动化测试执行与管理的平台

**核心功能**:
- 测试用例管理
- 自动化执行引擎
- 测试结果分析
- 缺陷自动关联
- 测试报告生成

**涉及团队**: NMC、会议主机
**共建方式**: 综合管理部提需求，基础设施团队建设
**里程碑**:
- 5月底: 基础版上线
- 6月底: 完整版上线

#### 3.1.3 度量平台（高优先级）

**需求描述**: 研发效能数据采集、分析、报告平台

**核心功能**:
- 数据采集（代码提交、构建、测试、发布）
- 效能指标计算（交付周期、缺陷率、AI采纳率）
- 可视化报表
- 趋势分析
- 基线管理

**涉及团队**: 无线、会议主机、综合管理部（全团队）
**共建方式**: 综合管理部主导，基础设施团队支撑
**里程碑**:
- 4月底: 数据采集启动
- 5月底: 基线建立
- 5月底: 效能报告v1上线
