# TR - 技术评审系列

> **阶段类型**：技术评审（Technical Review）  
> **阶段定位**：确保技术方案和产品质量达标  
> **争议升级**：TR2-TR7争议上升到研发体系主管决策

---

## 一、系列概览

### 1.1 TR系列定位

TR系列是IPD流程中的**技术质量保障评审体系**，贯穿从用户需求到版本发布的全过程。确保每个技术节点的质量达标，防止缺陷向下游传递。

### 1.2 TR系列阶段划分

```
TR1 → TR2 → TR3-1 → TR3-2 → TR4系列 → TR5系列 → TR6 → TR7
│      │      │       │        │         │        │      │
│      │      │       │        │         │        │      └─ 版本正式发布
│      │      │       │        │         │        └─ 版本预发布
│      │      │       │        │         └─ 集成验证（联调/转集成/PVT/SIT/集成转系统）
│      │      │       │        └─ 开发验证（模块设计/编码/EVT/SDV-DVT）
│      │      │       └─ 总体测试策略
│      │      └─ 软硬总体设计
│      └─ 系统需求&技术方案&选定制造商
└─ 用户需求
```

### 1.3 所属DCP阶段

| TR节点 | 所属DCP阶段 |
|--------|-------------|
| TR1 - TR3-2 | DCP3（产品计划） |
| TR4 - TR5-A | DCP4（Beta发布） |
| TR6 | DCP5（上市发布） |
| TR7 | DCP6（默认发货） |

## 二、TR1 - 用户需求

### 2.1 活动目的/意图

- 把关用户需求的质量，确保达到立项意图和目标
- 能够实现价值兑现和形成商业闭环
- 把关用户需求的价值Playbook和交付的Playbook清晰准确

### 2.2 准入准出

**准入条件**（PDT经理）：产线OKR导出的规划项 OR 系统月度导入

**准出标准**（PDT经理）：Roadmap（包含时间计划）+ 组织CDT开工会

**准入条件**（PDT规划代表）：产线OKR导出的规划项 / 市场OR导入

**准出标准**（PDT规划代表）：市场洞察过程信息 + 市场洞察结论 + 规划基调

**准入条件**（PDT软件研发代表）：产线OKR导出的规划项 / OR导入（客服）

**准出标准**（PDT软件研发代表）：关键技术突破结果 + 质量分析结果 + 质量版本规划

### 2.3 权责决策

| 角色 | 参与类型 | 核心职责 |
|------|----------|----------|
| PDT经理 | **评审表决** | 把关用户需求质量，确保达到立项意图和目标 |
| PDT规划代表 | **发起&评审表决** | 把关用户需求质量和用户体验；把关价值Playbook和交付Playbook清晰准确 |
| PDT软件研发代表 | **评审表决** | 把关需求技术可达性，确保没有不可实现的需求 |
| PDT国内市场代表 | **建议参评** | 把关需求和价值的市场预期匹配 |
| PDT协作部门 | **评审表决** | - |
| 软件研发代表扩展团队 | **建议参评** | - |
| 国内市场代表扩展团队 | **建议参评** | - |

### 2.4 质量风险

| 风险 | 来源角色 |
|------|----------|
| 研发预研不充分，导致到客户真实场景效果无法达成 | 业务ST团队 |
| 对用户场景理解不充分，功能做出来到真实环境用不起来 | PDT经理 |

### 2.5 质量关注点（各角色在TR2阶段的非功能性需求输入）

| 角色 | 关注点 |
|------|--------|
| PDT规划代表 | 性能参数和指标 |
| PDT软件研发代表 | 稳定性指标及需求 |
| PDT国内市场代表 | 硬件故障的可靠性保证 |
| PDT国际市场代表 | 软件可靠性需求 |
| PDT服务代表 | 系统韧性需求 |
| PDT硬件研发代表 | 系统Safety需求 |
| PDT供应链代表 | 系统隐私需求 |
| PDT协作部门 | 日志与可调试性保证 |
| 产品线ST代表 | 可维护性保证 |
| 规划代表扩展团队 | 兼容性 |
| 产线设计代表 | 安全性保证 |
| 协作部门规划代表 | 对公司其他产品或组件的影响 |
| 研发技术代表（架构师/专家） | 这些非功能性需求的设计被轻视，往往导致严重质量问题 |

## 三、TR2 - 系统需求&技术方案&选定制造商

### 3.1 活动目的/意图

- 把关**非功能性需求**的完整性及验收目标合理性
- 把关**功能性需求**的正常、异常场景全面性
- 从用户场景角度对系统需求检视，确保合理性和场景完备性

### 3.2 准入准出

**准入条件**（PDT规划代表）：规划基调评审结果 + CDT开工会

**准出标准**（PDT规划代表）：charter文件+签字表

**准入条件**（PDT软件研发代表）：产品规划表 + 用户需求

**准出标准**（PDT软件研发代表）：系统需求文档（按模板）+ 需求矩阵

**准入条件**（PDT硬件研发代表）：规划基调评审结果 + CDT开工会

**准出标准**（PDT硬件研发代表）：硬件可行性分析报告 + 预研结果评估

### 3.3 权责决策

| 角色 | 参与类型 | 核心职责 |
|------|----------|----------|
| PDT经理 | **评审表决** | - |
| PDT规划代表 | - | - |
| PDT软件研发代表 | **评审表决** | 把关非功能性需求完整性、功能性场景全面性、系统需求合理性 |
| PDT国内市场代表 | **建议参评** | - |
| PDT协作部门 | **评审表决** | - |
| 软件研发代表扩展团队（架构师/专家） | **评审表决** | 把关版本整体架构设计质量、DFX设计正确性 |
| 产线设计代表 | **评审表决** | 把关DFX需求纳入系统需求范围；把关产品交付设计符合客户使用旅程 |

### 3.4 质量风险

| 风险 | 来源角色 |
|------|----------|
| 架构设计不合理，极易引发问题或特别难查修复，质量不可控 | 业务ST团队 |
| 芯片选型有无法满足需求的地方；选用了质量不可控的第三方能力 | PDT经理 |
| 稳定性指标及需求 | PDT软件研发代表 |
