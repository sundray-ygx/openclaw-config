## 一、整体架构

> 来源：IPD2.0主干流程概览.png + 信锐IPD各节点角色全景表.xlsx

### 1.1 顶层决策阶段（DCP 系列）

DCP（Decision Checkpoint）是产品开发的**商业决策评审点**，决定项目是否继续投资。

```
DCP0          DCP1          DCP2-1          DCP2-2         DCP3          DCP4          DCP5           DCP6
产品规划SP → 年度规划BP → 立项决策(规划基调) → 立项决策(charter) → 项目计划决策 → Beta发布决策 → 上市发布决策 → 默认发货决策
```

**核心理念**：以**产品包**为中心，端到端保障**客户满意**和**需求满意**。

| 阶段 | 名称 | 核心目的 | 发起人 |
|------|------|----------|--------|
| DCP0 | 产品战略SP | 市场洞察→战场选择→业务设计（战略意图+价值主张+竞争策略）→质量投入→三代规划 | 业务ST团队 |
| _SPBP对应_ | _市场洞察及战场选择 + 业务设计-如何赢_ | _对应SPBP文档第一、二部分_ | _产线主导_ |
| DCP1 | 年度规划BP | 战略解码为年度OKR→关键举措和里程碑→产品路标→组织建设→风险消除 | PDT经理 |
| _SPBP对应_ | _年度规划解码_ | _对应SPBP文档第三部分_ | _产线主导_ |
| DCP2-1 | 立项决策（规划基调） | 明确客户/市场选择、商业价值、价值主张，初步确认技术/成本可行 | PDT规划代表 |
| DCP2-2 | 立项决策（charter） | 完成charter开发，确定产品构想、技术可行性和投资回报 | PDT经理（CDT团队） |
| DCP3 | 项目计划决策（TR1-TR3） | 把关产品包推出节奏，确保与商业闭环节奏匹配 | PDT经理 |
| DCP4 | Beta发布决策 | 把关产品包质量，确保达到Beta发布标准 | PDT经理 |
| DCP5 | 上市发布决策 | 把关产品在beta验证阶段的效果，确保达到上市标准 | PDT经理 |
| DCP6 | 默认发货决策 | 把关产品达到默认发货标准，消除发货风险 | PDT经理 |

### 1.2 技术评审阶段（TR 系列）

TR（Technical Review）是**技术质量评审点**，确保技术方案和产品质量达标。

```
TR1 → TR2 → TR3-1 → TR3-2 → TR4系列 → TR5系列 → TR6 → TR7
需求   系统需求   总体设计  测试策略  开发验证  集成验证  预发布  正式发布
```

| 阶段 | 名称 | 核心目的 |
|------|------|----------|
| TR1 | 用户需求 | 把关用户需求质量，确保达到立项意图和目标 |
| TR2 | 系统需求&技术方案&选定制造商 | 把关非功能性需求完整性、功能性场景全面性 |
| TR3-1 | 软硬总体设计 | 把关产品整体架构设计的合理性和场景完备性 |
| TR3-2 | 总体测试策略 | 把关测试目标、全局策略和风险消除有效性 |
| TR4 | 模块设计 | 把关模块设计任务书的合理性和场景完备性 |
| TR4 | 编码 | 确保需求达到准入标准，迭代资源到位 |
| TR4 | 一版样机EVT | 硬件一版样机验证 |
| TR4-A | 硬件研发定型(SDV/DVT) | 验收需求的实现效果，确保客户价值兑现 |
| TR5 | 联调 | 验收转出需求完整性，确保不遗漏 |
| TR5 | 转集成 | 把关产品测试报告，确保达到转系统质量标准 |
| TR5-A | 完成小批量(PVT)/SIT | 把关产品测试报告，确保达到预发布质量标准 |
| TR6 | 版本预发布 | 把关beta开局报告和正式发布测试报告 |
| TR7 | 版本正式发布 | 把关版本上市后质量运营策略 |

### 1.3 市场评审阶段（MR 系列）

MR（Marketing Review）是**市场策略评审点**，确保产品价值的有效市场传递。

| 阶段 | 名称 | 核心目的 |
|------|------|----------|
| MR1&2 | 市场营销计划 | 共识市场策略和计划，识别影响价值营销的风险 |
| MR3 | 市场营销预发布 | 检视各项上市准备完成情况，规避准备不足风险 |

### 1.4 服务评审阶段（SR 系列）

SR（Service Review）是**服务能力评审点**，确保产品的可交付性和售后保障。

| 阶段 | 名称 | 核心目的 |
|------|------|----------|
| SR1&2 | 服务计划 | 把关服务侧可服务性需求，确保服务上市计划合理 |
| SR3 | 服务预发布 | 把关可服务性需求验收结果，确保服务装备达标 |

### 1.5 全生命周期阶段

| 阶段 | 子阶段 | 核心目的 |
|------|--------|----------|
| 量产和变更 | 需求计划/变更计划/变更验证/入库/飞行检查/抽检 | 确保量产质量和变更可控 |
| 客户成交闭环 | 商机/POC测试/售前/方案设计/商务谈判/项目下单 | 实现客户价值闭环 |
| 交付阶段 | 需求沟通/实施方案/项目交付/验收/收尾 | 确保交付质量和客户满意 |
| 运维阶段 | 问题响应/问题处理/问题闭环/商机拓展 | 持续运维保障和价值拓展 |

## 三、通用决策机制

### 3.1 评审决策原则

1. **体系共识**：各PDT代表代表领域和体系的整体意见，会前需先做好体系内沟通和共识
2. **提前预审**：会议前发起人提前发起电子流评审（建议提前48小时），各评审表决人会前查阅并至少提1个问题
3. **严肃表决**：各评审表决人参会不遗漏，充分发表意见，一人一票严肃表决
4. **全票通过制**：评审决策采用全票通过制

### 3.2 争议升级机制

| 评审类型 | 争议最终决策人 |
|----------|----------------|
| DCP / MR / SR / TR1 | PDT经理 |
| TR2 - TR7 | 研发体系主管 |

### 3.3 授权原则

1. 可授权但不授责
2. 授权给本领域角色，保障领域专业度
3. 授权对象不能即当运动员又当裁判

### 3.4 角色参与类型

| 参与类型 | 说明 |
|----------|------|
| **发起** | 主导活动开展，对结果负责，包含评审前内容准备、发起会议评审、保障会议纪要闭环 |
| **评审表决** | 代表领域做商业决策/技术评审，把关风险，提出问题和建议，投票表决 |
| **建议参评** | 关联领域专家角色或关键下游角色，建议参与评审，补充专业意见，不参与表决 |
| **按需参与** | 基于前期研讨未达成一致的，由PDT代表按需邀请参与，不表决 |
| **综合管理部** | 负责事前流程赋能、电子流预审、评审决策过程规范及引导、会后基线会议结论 |

## 五、流程设计意图

> 来源：01_流程设计意图.md

1. 期望通过一个全局负责人，去主动推动项目联合开发到交付客户全流程的时间计划、项目质量的目标达成
2. 对于全局负责人、从权责定义上他的责任就是要端到端解决问题
3. 能够实现端到端把信息（软、硬、供应、行销）透明
4. 全局负责人真的有足够的权责、意愿，能推得动
5. 产品线对产品成功负责，产线需要去推动干系方在各个环节的问题解决
