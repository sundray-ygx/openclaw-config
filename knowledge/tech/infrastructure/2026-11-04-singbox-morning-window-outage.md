# sing-box 每日 08:00 定时故障窗口诊断（早间简报 GitHub 板块缺失根因）

- **日期**: 2026-11-04
- **状态**: 方案一已批准执行（cron 错峰 08:35 + 08:02 轮转守卫），待明早自然验证
- **性质**: 排查报告（sing-box / 机场代理 / 早间简报）

## 一句话结论

机场自 11-02 起每日 00:00 UTC（北京 08:00）轮转入口 IP，旧 IP 立即停止接受新连接；sing-box 侧 DNS 缓存最长 30 分钟内继续拨旧 IP → 新建出站会话全部 `i/o timeout`。早报 cron 恰在 08:00:00 整点触发，100% 撞进死窗 → GitHub 双仓库/热榜经代理全失败。08:30 左右缓存过期自然恢复。**容器、配置、订阅均无问题；纯上游行为 + 时序碰撞。**

## 现象

- 11-02/03/04 连续三天早报（08:00 cron）中 GitHub 板块经 1080 代理全部失败（curl rc=7）
- 事后巡检（09:20+）代理一切正常（204/0.79s），容器 6 天 0 重启、全程日志 0 条结构性错误

## 排查时间线（证据链）

1. **容器层**：running、0 restart、无 OOM；`docker logs` 全程仅 38 条 ERROR，无异常模式 → 排除容器故障
2. **实时验证**：`curl --proxy socks5h://127.0.0.1:1080 https://www.gstatic.com/generate_204` → 204/0.79s → 故障是时段性的，非持续性（修正今早诊断"机场数据面持续瘫痪"的结论）
3. **故障窗口锁定**：11-04 ERROR 全部落在 UTC 00:00:15–00:30:36（北京 08:00–08:30），错误完全一致：`failed to create session: dial tcp <IP>:35675: i/o timeout`，全部经 us-auto 组选中节点 San Francisco09a
4. **IP 轮转实锤**：三天拨的"死 IP"各不相同——11-02 `18.180.78.221`、11-03 `3.113.18.53`、11-04 `13.196.197.238`（均 AWS 日本区域段）；三个旧 IP 现在实测 TCP 全部超时（永久失效，非抖动）；当前 `us09a.t11-a.app` 已解析到新 IP `13.196.201.135` 且代理正常
5. **同窗口对照**：10-31 / 11-01 同窗口 ERROR 数 = 0 → 每日轮转是 11-02 起的新行为（与 11-02 起热榜连续缺失、11-03/04 简报 GitHub 板块缺失完全吻合）
6. **为何没自动切节点**：窗口内 12 节点 urltest 健康检查（gstatic，每 5 分钟）**0 报错**——anytls 会话复用让健康检查走已建立连接，探不出"新建会话失败"，us-auto 组始终认为 SF09a 健康，不切换（会话池蒙蔽效应）
7. **为何 30 分钟自愈**：最后失败 00:30:36、01:19 实测已恢复，与 DNS TTL≈1800s 过期后重新解析新 IP 的时间线吻合（TTL 未直接验证，由恢复时刻反推）

## 根因分层

| 层 | 问题 | 性质 |
|---|---|---|
| L1 机场 | 11-02 起每日 00:00 UTC 轮转入口 IP，旧 IP 即刻拒绝新连接（存量连接保留） | 上游行为，不可控 |
| L2 sing-box | DNS 缓存 ≤30min 持续拨死 IP；urltest 被会话池蒙蔽不触发切换 | 结构性，无法用配置根治（会话复用是内部行为） |
| L3 早报 cron | `0 8 * * *` 整点触发，恰好落在死窗起点 | 时序碰撞，可避 |

## 修复方案（待决策）

### 方案一（推荐）：错峰 + 轮转守卫
1. **早报 cron `0 8` → `35 8`**：避开最坏 30 分钟死窗（TTL 上界）+ 5 分钟裕量。零风险，一行改动。代价：简报晚 35 分钟到。
2. **新增守卫 cron `2 0 * * *`**（北京 08:02）：探活脚本 probe→死则 `docker restart sing-box` 强制重新解析→复测→落日志 `/var/log/proxy-rotation-guard.log`。若 DNS 权威侧即时生效，死窗从 30 分钟压到 ~2 分钟（明日守卫日志见分晓）；若 223.5.5.5 边缘缓存也持有旧记录，重启无效也不伤——脚本幂等，代理健康时零动作。

### 方案二（最小动作）：只错峰 08:35
不动 sing-box，纯 crontab 一行。死窗每天仍在（08:00–08:30 期间任何代理消费者，如 agent-reach 的 exa/web 调用会失败），但简报恢复确定。

### 方案三（方案一 + 效率项）：再加 CN reach 免代理
今早日志实证：8 篇国内媒体文章（cyzone/woshipm/qbitai/tmtpost）正文抓取失败，根因是 `REACH_ENV` 强制全部流量走代理、撞上死窗。给国内域名加 NO_PROXY/直连分支可根治此类连带损伤，同时降低日常延迟。改动限于 morning_briefing.py，需回归测试。

### 不做什么
- 不重启/不改 sing-box 配置结构（配置正确，cache.db 持久化正常）
- 不刷新订阅（节点域名未变，轮转是 IP 级，订阅刷新无济于事）
- 不换机场/加备用机场（套餐到 2027-04，当前每日 30 分钟窗口可工程化规避，性价比待观察）
