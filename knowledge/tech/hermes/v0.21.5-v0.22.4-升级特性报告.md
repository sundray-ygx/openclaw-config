## 2. 核心特性详解

每个特性四段式：是什么 → 解决什么问题 → 应用场景 → 技术实现原理。

### 2.1 单机单网关多 profile（Gateway Multiplexing）

- **是什么**：整台机器只跑一个 messaging gateway 进程，服务所有 profile；每个 profile 保留自己的凭据、allowlist、cron、会话。
- **解决什么问题**：此前每 profile 一个网关进程，进程数与 profile 数线性增长，内存占用高、token 冲突、启停多对象难管理。本机历史上正是网关类进程内存压力导致被 systemd KILL。
- **应用场景**：一台服务器跑多套隔离 agent（工作/个人/实验），或 bot 群。本机当前单 profile（default + scheduler 兄弟快照），为未来扩展留了余量。
- **技术实现原理**：`hermes update` 自动把 per-profile 网关折叠进复用型默认网关；webhook 平台按 `/p/<profile>/` 路径区分；`gateway.standalone: true` 可临时退出复用；`hermes -p X gateway stop|start` 可单独停泊某个 profile。

### 2.2 世代化更新 + 统一包管理 `hermes pm`（更新不可半途失败）

- **是什么**：所有依赖环境（Python、uv、Node、ripgrep、FFmpeg、Chromium 等）由统一包管理器管理，pin + 哈希校验；更新先构建全新"世代"，通过自检后才切换。
- **解决什么问题**：更新中途断电/被杀导致环境半新半旧、无法启动。本机 10-09 就发生过一次 update 被中断（apply 阶段退出），留下"欠账"由本次更新自动补完——正是该机制的直接受益。
- **应用场景**：无人值守服务器、systemd 托管的长跑网关；升级失败后重跑 `hermes update` 会自动续完欠账。
- **技术实现原理**：环境以世代（generation）为单位，新世代构建+校验通过才原子切换；失败保留旧世代继续服务；`hermes pm gc` 回收旧世代（实测有主机 92GB → 18GB）。被杀的更新下次启动自修复。运行时升级到 Python 3.14.7（pm 自动安装接管）。

### 2.3 稳定发布通道（Stable Release Channels）

- **是什么**：发布改走测试过的 SemVer tag；git 安装默认从"跟 main 每次 commit"改为"跟 stable 版本到版本"。
- **解决什么问题**：此前 git 安装默认追 main，一次 update 可能引入未验证的上游变更；升级风险不可控。
- **应用场景**：生产服务器追 stable；开发者可用 `hermes update --set-channel main` 切回前沿。降级到旧版本被标记为 rollback，永不静默发生。
- **技术实现原理**：每个 release 通过发布门（源 CI、Docker、Nix、签名桌面、全 OS 安装/升级演练）后才 publish；更新检查从每 30 分钟 `git fetch` 改为每天一次 GitHub API 调用（减载）。

### 2.4 提示词与代码库瘦身（Leaner）

- **是什么**：源码 1.06M → 698K 行（−34%），`gateway/run.py` 从 34,847 行缩到 5,512 行；固定提示词减 ~2.1k tokens；19 个少用工具改为按需加载（agent 搜索到才注入 schema）。
- **解决什么问题**：每次调用的固定 token 开销大、桌面工具 schema 占用高；代码臃肿维护难。
- **应用场景**：长会话/消息平台 DM 场景（如本机飞书通道）每轮都省 token，直接降成本、提响应速度。
- **技术实现原理**：零行为变更的等价重构；工具懒加载（lazy loading）——工具定义仍在，schema 只在 agent 主动检索时注入上下文。

### 2.5 Reasoning Replay + 提供商故障等待

- **是什么**：推理过程（reasoning）在 resume/分支/压缩后默认重放；提供商 503/529/超时时按可见的有限周期等待，而不是立刻终止回合。
- **解决什么问题**：长多步任务中途上下文切换丢失"思路"；自定义网关瞬时抖动导致整轮作废、需人工重发。
- **应用场景**：本机走自定义端点（api.ygxpro.online，GLM-5.3），网络抖动恢复能力强化的直接受益方；`agent.auto_recovery_cycles`（默认 5）控制等待上限。
- **技术实现原理**：所有能读 reasoning 的提供商默认重放（跨 resume/branch/compaction 保持前缀一致）；限流退避为有界循环（visible, bounded cycles）；自动路由绝不悄悄计费到用户没选的提供商。

### 2.6 cron 存储不可写检测

- **是什么**：cron store 写不进时，`doctor`、home-channel 和 cron 自身都会发警告。
- **解决什么问题**：定时任务静默失效。本机 10-09 曾发生升级提醒在触发时刻因调度器停机被 grace window 静默移除——此类"无声丢失"从此有告警面。
- **应用场景**：依赖 cron 做提醒/值守的无人服务器。
- **技术实现原理**：cron 引擎写 jobs.json/executions.db 失败时上报告警事件（v0.21.6 窗口引入），配合 doctor 检查项。

### 2.7 config.yaml 自愈 + 更安全的 hermes config

- **是什么**：config.yaml 损坏时自动回退到最后一份良好副本；`hermes config get` 掩码密钥（`--raw` 例外）；`set` 拒绝疑似拼错的路径。
- **解决什么问题**：手改配置一个缩进错误就让网关起不来（飞书通道全断）；密钥被 `config get` 打到日志里。
- **应用场景**：飞书 allowlist、平台凭据等关键配置的防误操作保护网。
- **技术实现原理**：写入前快照良本；读取失败回退良本并告警；路径校验白名单。

### 2.8 state.db 可靠性与会话自动清理

- **是什么**：state.db 锁超时点名持锁进程、busy 不再杀回合；`sessions.auto_prune` 默认开启（结束且 90 天不活跃的会话启动时删除，pinned/打开的永不动）；新增 `hermes sessions set-journal-mode|repair-profiles|repair-prompts` 修复命令。
- **解决什么问题**：会话库无限膨胀；锁竞争导致的回合失败。
- **应用场景**：本机**已显式关闭** auto_prune（`sessions.auto_prune: false`），因存量会话含 openclaw 时代历史记录，保留价值大于空间收益（磁盘 67% 用量，尚余 13G）。
- **技术实现原理**：VACUUM 仅在 25% 可回收时执行；PID 命名空间隔离防 lease 被偷。

### 2.9 安全修复（v0.21.6，全部包含在本次升级内）

| 修复 | 类型 | 本机暴露面（升级前评估） |
|---|---|---|
| Dashboard 认证 ×4（X-Forwarded-For 绕限流 / 审计日志无界写入 / /auth/ 无请求体限制 / 登录码劫持） | 认证绕过/DoS | 未运行 dashboard，不暴露 |
| **Git filter 硬化**：不可信仓库的 clean/smudge/process 过滤器程序可在首条 prompt 前执行（RCE 类） | RCE | 与本机每日 3 条 git 自动化链路同域，升级后免疫 |
| Email 网关 `From` 头引用显示名绕过 allowlist | 身份伪造 | 未启用 email 平台，不暴露 |

### 2.10 回合看门狗（Turn Liveness Watchdog）

- **是什么**：`agent.turn_liveness.timeout_s`（默认 600s）中断无进展的回合并释放会话。
- **解决什么问题**：模型/流挂死导致会话被无限占用（消息通道"卡死"表象）。
- **技术实现原理**：监控回合推进信号，超时中断；重复的 transcript 修复收敛为单一错误上报。

## 5. 升级排障实录（本机实踩 3 坑，下次避雷）

### 5.1 缺 clang++ → venv 构建失败

- **症状**：`Update preparation failed: venv: uv sync exited 1`，根因 `python-olm`（Matrix 加密可选依赖链 `hermes-agent[matrix] → mautrix[encryption]`）源码构建需要 clang++。
- **解法**：`yum install -y clang`（本机 Alibaba Linux 8，装到 clang 15.0.7）。
- **要点**：世代化机制保证此失败不损伤运行中的旧环境——直接修完重跑 `hermes update` 即可。

### 5.2 假 gh wrapper 写坏 GitHub token → stable 版本解析失败

- **症状**：`Could not resolve the stable source channel: Invalid header value b'Bearer GitHub authentication required\n...'`——认证头里有换行。
- **根因**：`/usr/local/bin/gh` 是一个"临时 wrapper"脚本（真 gh 在 `/usr/bin/gh`）。hermes 解析 stable 版本时调 `gh auth token`，wrapper 输出的是提示文本（含换行）而非 token，被写入 `~/.github_token` 又读回作 Bearer 头。
- **解法**：`mv /usr/local/bin/gh /usr/local/bin/gh.wrapper-broken`（移出 PATH）；`rm -f ~/.github_token`（匿名 API 可用；如需认证可 `gh auth token`（真 gh）> ~/.github_token，chmod 600）。
- **识别特征**：错误信息里出现 "Token saved to ~/.github_token" 即中招；`head -c 80 ~/.github_token` 见多行文本可确认。

### 5.3 网关会话内无法自我重启

- **症状**：`hermes gateway restart` / `systemctl restart hermes-gateway` 被拒——"cannot restart the gateway from inside the gateway process"（SIGTERM 会先杀掉命令自身）。
- **解法**：从网关进程树外部执行——SSH 直连 shell、systemd timer，或委派子代理（本次采用 delegate_task 子代理执行 systemctl restart，成功）。

### 5.4 教训：升级提醒别依赖被升级的系统自身

10-09 的升级提醒设在 hermes cron（23:00 触发），触发时刻调度器恰好停机（grace window 120s 过期）被静默移除，提醒丢失、升级搁置 13 天。**关键时间点的提醒应放 root crontab（不依赖被升级对象）**。
