# NAS 备份失败根因诊断报告
**诊断时间**: 2026-06-06 11:30
**问题**: NAS 备份连续 3 天失败（6/4, 6/5, 6/6）

---

## 一、问题现象

| 日期 | 备份状态 | 失败原因 |
|------|----------|----------|
| 2026-06-02 | ✅ 成功 | HTTP 201 |
| 2026-06-03 | ✅ 成功 | HTTP 201 |
| 2026-06-04 | ❌ 失败 | HTTP 000 (Connection refused) |
| 2026-06-05 | ❌ 失败 | HTTP 000 (Connection refused) |
| 2026-06-06 | ❌ 失败 | HTTP 000 (Connection refused) |

---

## 二、根因分析

### 2.1 直接原因
**备份脚本配置的 WebDAV URL 错误**
- 脚本配置: `WEBDAV_URL="http://47.119.177.194:5005"`
- 实际 WebDAV 服务: `http://127.0.0.1:5000` (Synology DSM)
- FRP 隧道配置: NAS 端口 5000 → 远程端口 5000

### 2.2 为什么 6/2、6/3 成功？
**可能的解释**:
1. **之前的配置可能是正确的** - 脚本可能在某个时间点被修改，从 5000 改为 5005
2. **Nginx 反向代理曾经有效** - Nginx 配置了 `proxy_pass http://127.0.0.1:5005`，但本地没有服务监听 5005
3. **历史成功可能是误报** - 需要进一步验证 6/2 和 6/3 的实际备份是否存在于远程

### 2.3 为什么 6/4 开始失败？
**关键时间节点**:
- 6/3 22:29 - Nginx 服务重启（systemd restart nginx）
- 6/4 02:00 - 备份首次失败

**推论**:
- Nginx 重启后，反向代理配置生效，但后端 5005 端口无服务
- 所有流量被代理到不存在的服务，导致 Connection refused
- 脚本从未真正连接到正确的 WebDAV 服务

### 2.4 架构问题

**当前错误架构**:
```
备份脚本 → http://47.119.177.194:5005 (无服务)
    ↑
Nginx 反向代理 (webdav.conf)
    ↓
127.0.0.1:5005 (无服务监听)
```

**正确架构应该是**:
```
备份脚本 → http://127.0.0.1:5000 (Synology WebDAV)
    ↓
FRP 客户端 (nas: 5000 → 5000)
    ↓
FRP 服务端 (47.119.177.194:5000)
    ↓
NAS 设备 (WebDAV 服务)
```

## 三、验证发现

### 3.1 端口监听状态
- ❌ 端口 5005: 未监听 (Nginx 反向代理后端)
- ✅ 端口 5000: 正常监听 (Synology DSM)
- ✅ Nginx: 运行正常 (监听 80/443/8080)

### 3.2 连接测试
```bash
# 直接连接 WebDAV 服务（正确）
curl http://127.0.0.1:5000/ → HTTP 200 (Synology DSM 页面)

# 通过 Nginx 反向代理连接（错误）
curl http://47.119.177.194:5005/ → Connection refused
```

### 3.3 FRP 配置
```toml
[nas]
type = "tcp"
local_ip = "127.0.0.1"
local_port = 5000  # NAS 本地端口
remote_port = 5000 # FRP 远程端口
```

**结论**: FRP 配置正确，端口映射为 5000 → 5000

### 3.4 Nginx 配置问题
```nginx
# /etc/nginx/conf.d/webdav.conf
location / {
    proxy_pass http://127.0.0.1:5005;  # ❌ 错误端口
}
```

**问题**: Nginx 反向代理指向 5005，但实际 WebDAV 在 5000

## 四、根本原因总结

| 层级 | 问题 | 影响 |
|------|------|------|
| **配置层** | 备份脚本 WebDAV_URL 配置错误 (5005 → 应为 5000) | 直接导致连接失败 |
| **架构层** | Nginx 反向代理配置错误，指向不存在服务的端口 | 即使脚本正确也会失败 |
| **验证层** | 缺少备份验证机制，无法及时发现备份失败 | 3 天才发现问题 |

## 五、修复方案

### 方案 A：修复备份脚本配置（推荐）
**优点**: 直接、简单、不影响其他服务
**改动**: 修改 `nas_backup.sh` 中的 `WEBDAV_URL`

```bash
WEBDAV_URL="http://127.0.0.1:5000"  # 改为本地 5000 端口
```

**原理**: 直接访问本地 Synology WebDAV，无需经过 Nginx 反向代理

---

### 方案 B：修复 Nginx 反向代理
**优点**: 保持统一入口，便于管理
**改动**: 修改 `/etc/nginx/conf.d/webdav.conf`

```nginx
proxy_pass http://127.0.0.1:5000;  # 改为 5000 端口
```

**同时修改备份脚本**:
```bash
WEBDAV_URL="http://47.119.177.194:5000"  # 使用 Nginx 入口
```

**原理**: 通过 Nginx 反向代理访问，增加一层控制和日志

---

### 方案 C：使用 FRP 远程地址
**优点**: 支持异地备份，即使本地 WebDAV 临时不可用
**改动**: 修改备份脚本

```bash
WEBDAV_URL="http://47.119.177.194:5000"  # FRP 远程地址
```

**原理**: 通过 FRP 隧道访问 NAS，绕过本地依赖

---

## 六：推荐方案

**推荐方案 C（使用 FRP 远程地址）**

**理由**:
1. **可靠性**: 不依赖本地 WebDAV 服务，即使 NAS 重启也能备份
2. **灵活性**: 支持异地场景，脚本可运行在任何有网络的地方
3. **一致性**: 与现有 FRP 架构一致，无需额外配置
4. **简化**: 移除不必要的 Nginx 反向代理层

**执行步骤**:
1. 修改 `nas_backup.sh`: `WEBDAV_URL="http://47.119.177.194:5000"`
2. 测试备份: 手动执行脚本验证
3. 可选: 禁用/删除 Nginx webdav.conf 配置（无用配置）

```bash
rm -rf "$LOCAL_BACKUP_DIR"
```

**问题**: 当上传失败时，`$LOCAL_BACKUP_DIR` 已被删除，第二个命令会失败
**建议**: 使用绝对路径或变量保存路径
