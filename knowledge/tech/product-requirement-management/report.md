## 一、需求端到端闭环全景

### 1.1 全链路视图

```
市场洞察 → 战略规划 → 战略拆解 → 年度规划 → 版本Roadmap
    ↓                                              ↓
持续改进 ← 需求反馈 ← 需求闭环 ← 价值传递 ← 价值发布 ← 需求验收 ← 需求开发 ← 需求细化 ← 需求优先级
```

需求不是线性流水线，而是**螺旋上升的闭环**。每轮迭代带回市场反馈，驱动下一轮更精准的需求定义。

### 1.2 各环节定义

| # | 环节 | 核心问题 | 输入 | 输出 | 关键活动 |
|---|------|----------|------|------|----------|
| 1 | 市场洞察 | 市场发生了什么变化？客户真正要什么？ | 行业报告、客户反馈、竞品动态、销售线索 | 市场洞察报告、客户痛点清单、机会点 | 客户访谈、竞品分析、趋势研判、场景扫描 |
| 2 | 战略规划 | 我们要在哪些领域竞争？ | 市场洞察、公司战略、能力盘点 | 产品战略方向、目标市场定义、竞争策略 | SP（Strategic Planning）制定、赛道选择 |
| 3 | 战略拆解 | 战略如何落到产品线？ | 产品战略 | 产品线目标、关键战役 | BEM 拆解、里程碑设定 |
| 4 | 年度规划 | 今年做什么？不做什么？ | 战略拆解、资源约束 | 年度产品计划、资源分配 | BP（Business Plan）制定、投资组合决策 |
| 5 | 版本Roadmap | 按什么节奏交付？ | 年度规划 | 版本计划、特性规划 | 版本节奏定义、特性分批 |
| 6 | 需求优先级 | 先做什么？后做什么？ | 需求池、版本约束 | 优先级排序的需求列表 | 价值评估、依赖分析、ROI 排序 |
| 7 | 需求细化 | 这个需求到底要做到什么程度？ | 优先级需求 | 需求规格（SRS）、验收标准 | 需求分析、场景拆解、方案评审 |
| 8 | 需求开发 | 怎么实现？ | 需求规格 | 代码/产品 | 设计、编码、单元测试 |
| 9 | 需求验收 | 做对了吗？ | 需求规格、产品 | 验收结论 | 系统测试、客户验证、Beta |
| 10 | 价值发布 | 交付给客户了吗？ | 验收通过的产品 | 发布版本、发布说明 | 版本发布、升级方案 |
| 11 | 价值传递 | 客户知道怎么用吗？用起来了吗？ | 发布产品、客户信息 | 客户采纳率、使用数据 | 营销材料、培训、方案推广 |
| 12 | 需求闭环 | 需求是否达成了预期价值？ | 价值传递数据、客户反馈 | 价值评估结论 | 效果度量、客户回访 |
| 13 | 需求反馈 | 市场怎么说？下一步怎么调？ | 闭环结论、市场变化 | 新的需求输入、改进方向 | 客户满意度分析、需求池更新 |
| 14 | 持续改进 | 流程本身怎么变好？ | 反馈、度量数据 | 流程优化方案 | 复盘、流程优化、能力建设 |

## 二、IPD 视角下的需求管理

### 2.1 IPD 决策点与需求的关系

```
Charter → TR1 → TR2 → TR3 → TR4 → TR5 → TR6 → GA
  ↑        ↑      ↑      ↑      ↑      ↑      ↑      ↑
  |        |      |      |      |      |      |      |
 需求     需求   需求   需求   需求   需求   需求   需求
 立项     分析   设计   开发   集成   验证   发布   交付
 阶段     完成   完成   完成   验证   确认   就绪   运维
```

### 2.2 各节点需求管理要求

| IPD 节点 | 需求应达到的状态 | 需求相关活动 | 决策标准 |
|----------|------------------|--------------|----------|
| **Charter（立项）** | 需求方向明确，商业价值清晰 | 收集市场需求、定义产品包需求（OR）、初始优先级 | 市场空间足够、技术可行、战略对齐 |
| **TR1（需求分析完成）** | 需求基线化，覆盖完整 | 需求规格评审、需求追溯矩阵建立、需求承诺 | 需求完整、无歧义、可验证、干系人确认 |
| **TR2（方案设计完成）** | 需求与设计双向可追溯 | 需求→设计映射确认、接口需求确认 | 设计覆盖所有需求，无遗漏 |
| **TR3（开发完成）** | 需求变更受控 | 编码实现、需求变更评审 | 变更经 CCB 审批，影响分析完成 |
| **TR4（集成验证）** | 需求可验证 | 集成测试、场景验证 | 功能完整性确认 |
| **TR5（系统验证）** | 需求可验收 | 系统测试、客户场景验证 | 测试用例 100% 覆盖需求 |
| **TR6（发布就绪）** | 发布内容明确、价值可传递 | 发布范围确认、已知问题评估 | 发布需求列表与实际交付一致 |
| **GA（正式发布）** | 价值传递方案就绪 | 营销材料、培训、方案文档 | 传递材料齐全、渠道就绪 |

### 2.3 需求成熟度模型

```
Level 1: 想法（Idea）        — 有一个方向，但没有结构化描述
Level 2: 需求（Requirement）  — 已结构化描述，有场景、有验收标准
Level 3: 基线需求（Baselined）— 已评审、已承诺、纳入版本计划
Level 4: 已实现（Realized）   — 开发完成、通过验证
Level 5: 已交付（Delivered）  — 客户可用、价值数据可度量
```

**关键规则：进入 TR1 时，需求必须达到 Level 3（基线化）。**

### 2.4 需求变更控制

| 变更类型 | 触发条件 | 决策机制 | 影响范围 |
|----------|----------|----------|----------|
| 微调 | 措辞、补充场景，不影响方案 | 项目组内决策 | 低 |
| 一般变更 | 影响设计/工作量，不影响版本节奏 | PM + 研发负责人审批 | 中 |
| 重大变更 | 影响版本节奏、资源分配或战略方向 | CCB（变更控制委员会）决策 | 高 |

**原则：TR1 之后的需求变更，必须走正式变更流程，不允许口头变更。**

## 三、典型需求问题归因分析

基于过往典型问题，按环节归类：

### 3.1 需求没有统一收口

| 维度 | 分析 |
|------|------|
| **现象** | 销售、市场、研发、客户多渠道提需求，没有统一入口，需求重复、矛盾、遗漏 |
| **根因** | 缺乏需求管理的"单一入口"机制；产品经理没有被明确授权为需求唯一出口 |
| **影响** | 优先级打架、资源分散、做了A忘了B、客户感知混乱 |
| **改进方向** | 建立需求统一收口机制：所有需求必须进入统一需求池，由产品经理（或需求管理员）统一管理。设立需求评审会，定期对需求池进行清洗和优先级排序。 |

### 3.2 需求变更频繁

| 维度 | 分析 |
|------|------|
| **现象** | 开发过程中需求频繁变化，返工多，团队疲于奔命 |
| **根因** | TR1 前需求分析不充分；变更控制机制形同虚设；上游（市场/销售）给的信息不稳定但被直接传递 |
| **影响** | 开发效率低、版本节奏被打乱、质量下降、团队士气受损 |
| **改进方向** | ① TR1 前做足需求分析，宁可多花时间也不要带病进入开发；② 变更必须走 CCB，量化影响（工作量、节奏、风险）；③ 建立"需求冻结窗口"，开发阶段原则上不接收非阻断性变更 |

### 3.3 需求定义不清晰（需求治理能力弱）

| 维度 | 分析 |
|------|------|
| **现象** | 需求描述模糊，开发理解不一致，验收时扯皮 |
| **根因** | 需求写作质量差（缺场景、缺边界、缺验收标准）；评审流于形式；缺乏需求质量标准 |
| **影响** | 做出来的不是想要的；反复沟通成本高；测试无据可依 |
| **改进方向** | ① 建立需求质量 Checklist（至少包含：用户场景、前置条件、正常流程、异常流程、验收标准）；② 需求评审必须有研发和测试参与，且"能说不"；③ 需求模板标准化 |

### 3.4 价值传递效果不佳

| 维度 | 分析 |
|------|------|
| **现象** | 功能做完了，但客户不知道、不会用、没用起来；各方对"效果好不好"各说各话 |
| **根因** | 发布≠交付。只关注"做出来"，不关注"用起来"；缺乏价值度量的共识指标；市场/销售/产品对需求价值的预期没有提前对齐 |
| **影响** | 研发投入产出无法衡量；好功能沉没；客户续费/复购动力不足 |
| **改进方向** | ① 需求立项时就定义"价值度量指标"（采纳率、NPS、收入贡献等）；② 产品、市场、销售在需求立项时对齐价值预期；③ GA 后 90 天内做价值回溯 |

### 3.5 需求 PDCA 未闭环

| 维度 | 分析 |
|------|------|
| **现象** | 第一阶段做了，市场反馈不好，就没有第二阶段了。需求演进出断裂，没有持续迭代 |
| **根因** | 缺乏"需求→交付→反馈→演进"的闭环机制；反馈不好时倾向于"换方向"而非"分析原因并调整"；项目制思维（做完就散），没有产品生命周期视角 |
| **影响** | 前期投入沉没；产品缺乏持续竞争力；团队对"做需求"的价值感下降 |
| **改进方向** | ① 每个需求在立项时就规划演进路线（V1→V2→V3）；② 建立发布后复盘机制，分析反馈不好的原因（是需求定义问题？实现问题？还是传递问题？）；③ 用"需求生命周期能力"来评估和考核，而非"交付数量" |

## 四、好的需求应该怎么运转

### 4.1 理想态需求流转模型

```
                    ┌─────────────────────────┐
                    │     统一需求池            │
                    │  （唯一入口，统一管理）     │
                    └──────────┬──────────────┘
                               │
                    ┌──────────▼──────────────┐
                    │     需求评审与治理        │
                    │  （质量筛查、去重、分类）   │
                    └──────────┬──────────────┘
                               │
                    ┌──────────▼──────────────┐
                    │     优先级排序           │
                    │  （价值×紧迫×依赖×资源）  │
                    └──────────┬──────────────┘
                               │
                    ┌──────────▼──────────────┐
                    │     版本规划             │
                    │  （纳入Roadmap，明确版本） │
                    └──────────┬──────────────┘
                               │
                    ┌──────────▼──────────────┐
                    │     需求基线化（TR1）     │
                    │  （冻结，进入变更控制）    │
                    └──────────┬──────────────┘
                               │
                    ┌──────────▼──────────────┐
                    │     设计→开发→验证       │
                    │  （双向可追溯）           │
                    └──────────┬──────────────┘
                               │
                    ┌──────────▼──────────────┐
                    │     发布与价值传递        │
                    │  （客户用起来）           │
                    └──────────┬──────────────┘
                               │
                    ┌──────────▼──────────────┐
                    │     价值回溯与反馈        │
                    │  （度量→分析→改进）       │
                    └──────────┬──────────────┘
                               │
                    ┌──────────▼──────────────┐
                    │     需求演进             │
                    │  （V1→V2→V3，螺旋上升）  │
                    └─────────────────────────┘
```

### 4.2 关键角色与职责

| 角色 | 职责 | 核心权力 |
|------|------|----------|
| **产品经理** | 需求统一收口、优先级决策、需求质量把关 | 需求的唯一出口 |
| **系统工程师/SE** | 需求分析与拆解、技术可行性评估 | 需求"能不能做"的技术判断 |
| **研发负责人** | 需求实现、工作量评估、变更影响分析 | "做不做得了"的资源判断 |
| **市场/销售** | 市场需求输入、价值传递、客户反馈 | 客户需求的"第一手信息源" |
| **CCB** | 重大需求变更决策 | 变更的"刹车" |
| **PDT 经理** | 端到端交付负责、资源协调 | 版本节奏的"掌舵者" |

### 4.3 度量指标体系

**过程指标（管效率）：**

| 指标 | 定义 | 健康基线 |
|------|------|----------|
| 需求吞吐周期 | 需求从提出到GA的平均周期 | 按版本节奏监控趋势 |
| 需求变更率 | TR1后变更需求数/基线需求总数 | < 15% |
| 需求返工率 | 因需求问题导致的返工工作量/总工作量 | < 10% |

**结果指标（管效果）：**

| 指标 | 定义 | 健康基线 |
|------|------|----------|
| 需求交付偏差 | 实际交付vs计划交付的特性数差异 | < 10% |
| 价值达成率 | 发布后90天价值回溯达标的需求数/总交付需求数 | > 70% |
| 需求采纳率 | 客户实际使用的特性数/交付特性数 | > 60% |

**闭环指标（管演进）：**

| 指标 | 定义 | 健康基线 |
|------|------|----------|
| 反馈闭环率 | 有正式复盘的需求占总交付需求的比例 | > 80% |
| 需求演进率 | 进入V2及以上迭代的需求/总需求 | 趋势上升 |

## 五、改进建议与落地路径

### 5.1 分阶段推进

| 阶段 | 时间 | 重点动作 | 预期效果 |
|------|------|----------|----------|
| **第一阶段：止血** | 1-2月 | ① 建立需求统一收口机制（需求池+产品经理审批）；② 建立需求质量 Checklist；③ 变更控制流程落地 | 需求混乱局面得到控制 |
| **第二阶段：提效** | 3-6月 | ④ TR1 需求基线化标准落地；⑤ 建立需求追溯矩阵；⑥ 度量指标体系上线 | 需求质量和效率可度量 |
| **第三阶段：闭环** | 6-12月 | ⑦ 价值回溯机制建立；⑧ 需求演进路线规划；⑨ PDCA 闭环常态化 | 需求持续改进形成飞轮 |

### 5.2 周会讨论建议

以下问题适合在周会上引导讨论：

1. **收口问题**：大家觉得现在的需求主要从哪些渠道进来的？有没有漏掉的？谁在管？
2. **变更问题**：有没有哪个需求在开发过程中变了好几次？当时是怎么发生的？
3. **定义问题**：有没有做出来发现"这不是我想要的"？原因是什么？
4. **传递问题**：有没有做完的功能客户不知道或者不会用的？
5. **闭环问题**：有没有做了V1之后就没有然后的功能？

### 5.3 成功标准

需求管理体系有效的标志：

- ✅ 每条需求都能追溯到源头（谁提的、为什么提）
- ✅ 进入开发的需求都经过正式评审和基线化
- ✅ 变更有审批、有记录、有影响分析
- ✅ 发布后有正式的价值回溯
- ✅ 好的需求被持续演进，差的需求有原因分析
- ✅ 团队对"需求是什么"的理解是一致的

## 附录：需求质量 Checklist

每个进入 TR1 的需求，必须通过以下检查：

- [ ] 有明确的用户场景（谁、在什么场景下、要解决什么问题）
- [ ] 有清晰的验收标准（怎样算"做完了"）
- [ ] 有价值度量指标（怎样算"做好了"）
- [ ] 无歧义（研发和测试的理解一致）
- [ ] 有优先级和版本归属
- [ ] 已考虑与其他需求的依赖和冲突
- [ ] 已考虑向后兼容和升级影响（对存量客户的影响）
