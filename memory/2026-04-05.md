# 2026-04-05 日志

### [PROJECT:OpenClaw] cron 重复触发问题排查

- **结论**: 不是 cron 重复触发，也不是 gateway bug。根本原因是**阿里云百炼 API 月配额耗尽**（429 rate limit），导致单次 cron run 内 failover 重试链路全部失败，最终 300s 超时
- **详细分析**:
  1. NAS 备份 cron（02:00）每天只触发**1次**，runs 记录正常
  2. 单次 run 内部，gateway 的 model failover 机制按顺序尝试所有 fallback 模型：
     - bailian/kimi-k2.5 → bailian/qwen3.5-plus → bailian/qwen3-max → bailian/qwen3-coder-next → bailian/qwen3-coder-plus → bailian/MiniMax-M2.5 → bailian/glm-5 → bailian/glm-4.7 → zai/glm-5 → zai/glm-5-turbo
  3. 所有 **bailian provider** 下的模型共享同一个 API Key（`sk-sp-f51b...`），**月配额是 provider 级别的**，不是 model 级别的
  4. 所以 failover 到任何 bailian 模型都会 429，只有 zai provider 的模型不受影响
  5. zai/glm-5 超时（102s），zai/glm-5-turbo 也失败 → 最终 300s timeout
- **失败模式**:
  - 4/1, 4/3, 4/5: 失败（超时），zai 也赶不上
  - 4/2, 4/4: 成功（failover 到了 zai/glm-5 并及时响应）
  - 规律：大约隔天成功/失败
- **实际影响**:
  - 每次失败产生 ~18-36 个 lane task error 日志（看起来像重复触发，实际是 failover 重试）
  - 备份脚本本身不受影响（实际在 exec 层成功执行），只是 LLM 汇报环节超时
  - 4/5 备份实际已完成（2:03 上传成功），只是 LLM session 超时未能汇报
- **根因**: 阿里云百炼 API Key 月配额耗尽（`429 month allocated quota exceeded`）
- **标签**: #cron #failover #rate-limit #bailian

### 建议（待 Boss 决策）

1. **短期**: 将 NAS 备份 cron 的 model 直接设为 `zai/glm-5`（绕过 bailian 限流）
2. **短期**: 检查百炼账户配额，充值或等月初重置
3. **长期**: 考虑 cron 任务的 failover 策略优化 — 当 provider 级别 429 时跳过该 provider 下所有模型
